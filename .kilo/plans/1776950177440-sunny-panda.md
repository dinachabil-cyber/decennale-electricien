# Dynamic Website Builder Refactor Plan

## Current State Analysis

After examining the codebase, I've identified the following key files related to the dynamic multi-step form and section system:

1. `frontend/src/components/Hero.jsx` - Main hero component with form logic
2. `frontend/src/config/formConfig.js` - Form step configuration and validation
3. `frontend/src/components/admin/sections/HeroSectionEditor.jsx` - Admin editor for hero sections
4. `frontend/src/config/sectionConfig.js` - Centralized section configuration system

## Issues Identified

### 1. Multi-Step Form (Hero Section)
- Configuration is partially centralized but duplicated between `FORM_CONFIG.STEPS` and hardcoded defaults in Hero.jsx
- Form data initialization has multiple pathways (static vs dynamic config)
- Validation logic is spread across `validateField`, `canProceedToStep`, and inline checks
- Submission preparation uses conditional logic based on config type
- The system works but has redundancy and complexity

### 2. Section System (CMS-like)
- Section configuration exists in `SECTION_CONFIG` but has duplication (form steps defined both in FORM_CONFIG and SECTION_CONFIG.hero.defaultContent.formConfig)
- Editor/renderer mapping uses string keys and dynamic imports which is good
- However, the hero section's form configuration is duplicated in multiple places
- Adding new section types requires updating multiple maps and maintaining consistency

## Proposed Solution

### 1. Unified Form Configuration System
Create a single source of truth for form configuration that eliminates duplication:

```
src/config/formSchema.js
export const FORM_SCHEMA = {
  // Global form options referenced by steps
  options: {
    LEGAL_STATUSES: [...],
    REVENUE_OPTIONS: [...]
  },
  // Form steps with full configuration
  steps: [
    {
      key: 'nom',
      title: 'Nom',
      label: 'Quel est votre nom ?',
      type: 'input',
      required: true,
      placeholder: 'Votre Nom *',
      icon: 'fa-user',
      autoFocus: true,
      validation: {
        required: true,
        minLength: 1,
        custom: (value) => value.trim().length > 0
      }
    },
    // ... other steps
  ]
};

// Helper functions exported for backward compatibility
export function getFormSteps() { return FORM_SCHEMA.steps; }
export function getFieldOptions(fieldKey) { /* ... */ }
export function initializeFormData() { /* ... */ }
// etc.
```

### 2. Simplified Hero Component
Refactor Hero.jsx to:
- Use the unified form schema directly
- Remove dynamic config vs static config branching
- Simplify form data initialization and validation
- Keep compatibility with submitQuote API through a standardized prepareSubmitData function

### 3. Section Configuration Improvements
Modify sectionConfig.js to:
- Reference the unified form schema instead of duplicating form step definitions
- Ensure hero section's defaultContent.formConfig points to the canonical form configuration
- Keep the editor/renderer mapping system as it's already well-designed

### 4. Validation System Enhancement
Create a reusable validation utility that:
- Takes field configuration and form data
- Returns validation errors based on field rules
- Can be used both in form validation and section validation
- Supports custom validation functions

### 5. Admin Editor Improvements
The HeroSectionEditor already has good dynamic capabilities but could benefit from:
- Using the unified form schema for default values
- Simplified field addition/removal that works with the canonical schema

## Implementation Steps

1. Create unified form schema file (formSchema.js)
2. Update formConfig.js to export from the schema (maintain backward compatibility)
3. Refactor Hero.jsx to use the unified schema
4. Update sectionConfig.js to reference the unified schema for hero form config
5. Ensure all validation logic uses shared validation utilities
6. Test that existing functionality remains intact
7. Verify that adding/removing form fields works through admin editor
8. Confirm backend submission compatibility

## Benefits

- Single source of truth for form configuration
- Elimination of switch/case and duplicated logic
- Easier maintenance when adding new form fields or section types
- Consistent validation across the application
- Clear separation of concerns
- Better developer experience for non-developers modifying configurations

## Optional Future Improvements

1. Implement JSON Schema validation for form configurations
2. Add drag-and-drop section reordering in page builder
3. Create form builder section type that allows creating custom multi-step forms
4. Add section-level validation that can prevent saving invalid configurations
5. Implement form field dependencies (show/hide based on other field values)
